# Расписание АИТУ

Next.js 16, React 19, PostgreSQL и Prisma 5. Локальная разработка — **http://localhost:3002**.

## Локальный запуск

Нужны Node.js 22+ и Docker с Compose. На macOS с Colima сначала `colima start` (в текущем окружении профиль `tkuik`: `colima start --profile tkuik`).

```sh
cp .env.example .env
npm ci
docker compose up -d db
npm run db:migrate
npm run accounts:setup
npm run schedules:import -- --campus=SECONDARY --apply
npm run dev
```

Если Homebrew установил Compose отдельной командой, используйте `docker-compose` вместо `docker compose`.
База доступна только локально на порту 55432, данные сохраняются в Docker volume. В `.env` должен оставаться адрес локальной базы; **не копируйте туда production DATABASE_URL**.

`accounts:setup` создаёт три аккаунта с независимыми случайными паролями:

| Логин | Права |
| --- | --- |
| `dispatcher1` | Изменение расписания и замен только 1 площадки (`MAIN`) |
| `dispatcher2` | Изменение расписания и замен только 2 площадки (`SECONDARY`) |
| `admin` | Обе площадки и общие настройки |

Пароли записываются в `.local/accounts-<timestamp>.json` с правами `0600`; этот каталог исключён из Git и Docker. Повторный запуск не меняет существующие пароли. Создание аккаунтов и пакетный импорт без специальных флагов разрешены только для локальных баз `tkuik_dev`/`tkuik_test`.

## Запуск приложения в Docker

Разработка на порту 3002 (остановите локальный `npm run dev`, если он занимает порт):

```sh
docker compose --profile dev up --build -d
```

Dev-контейнер использует Webpack с `WATCHPACK_POLLING=true`, чтобы изменения файлов надёжно подхватывались в macOS/Colima. Сервис `dev` применяет миграции только к локальному сервису `db`. Аккаунты и расписания инициализируются командами выше либо через `docker compose exec dev npm run accounts:setup` и `docker compose exec dev npm run schedules:import -- --campus=SECONDARY --apply`. Пароли, созданные внутри контейнера, находятся в `/app/.local/`; сохраните их до удаления контейнера.

Проверка production-сборки на своей локальной базе:

```sh
docker compose up -d db
npm run db:migrate
docker compose --profile production up --build -d
```

Production-контейнер слушает порт 3000 (можно задать `APP_PORT`), работает от непривилегированного пользователя и содержит standalone-сборку. Миграции не запускаются при старте production-приложения. `/api/health` проверяет подключение к БД.

Остановка без удаления данных: `docker compose --profile dev --profile production stop`.

## Расписания 2026/2027

Четыре оригинальных Excel-файла находятся в `data/schedules/2026-2027-sem1/`. Это расписания 2 площадки; соответствие проверено по существующей production-базе (группа 9ПО-22к — `SECONDARY`).

```sh
# Предпросмотр без записи в базу:
npm run schedules:import -- --campus=SECONDARY
# Запись всех четырёх курсов одной транзакцией, только в локальную БД:
npm run schedules:import -- --campus=SECONDARY --apply
```

Импорт сохраняет листы «числ» и «знам» независимо: пустая пара не заполняется из другой недели. Однолистовое расписание без указания недели получает тип `both`. Несколько преподавателей сохраняются отдельными записями подгрупп.

Для **9ПО-22к, пятница**: 1 пара «ИСТОРИЯ» — только числитель; 4 пара «ОСНОВЫ АЛГОРИТМИЗАЦИИ И ПРОГРАММИРОВАНИЯ» — только знаменатель. Это уже указано в исходном Excel, отдельного исправления предметов в коде нет.

Разбор и проверка файла происходят до удаления старых данных. Замена курса, добавление преподавателей и запись журнала объединены в транзакцию. Переданные курс и площадка проверяются. Импорты/изменения сериализуются блокировкой PostgreSQL.

## Доступ и журнал

Вход через `/admin/login`. Пароли хранятся как scrypt-хеши с индивидуальной солью; случайные токены сессий — в HttpOnly/SameSite cookie, в базе хранится только хеш токена. Сессия действует 8 часов; выход отзывает её. После 5 неверных паролей аккаунт блокируется на 15 минут. Запросы изменения проверяют источник, пользователя и площадку **на сервере**.

Журнал действий доступен в админке: входы, неудачные входы в существующие аккаунты, выходы, создание, изменение, удаление, импорты расписаний и замен. Изменение данных и запись журнала проходят в одной транзакции. Сохраняются автор, время, площадка, значения до/после. Диспетчер видит журнал своей площадки, администратор — общий. Пагинация по 50 событий.

Замены загружаются DOCX-файлом с выбранной площадкой. Все группы проверяются перед записью; неизвестная/чужая группа отклоняет импорт целиком. Пустые предмет и преподаватель разрешены для отмены пары. Старые замены получают площадку миграцией только при однозначном соответствии группе; неопределённые записи остаются доступны общему администратору через API.

Тип недели меняется в понедельник по московскому времени. Публичное чтение настроек не выполняет записей. Ручная настройка общего администратора задаёт дату отсчёта и сохраняется при последующих чтениях.

## Проверки

```sh
npm test
npm run typecheck
npm run build
npm audit
# При работающем локальном сервере и созданных аккаунтах:
npx tsx scripts/verify-api.ts
```

Интеграционная проверка создаёт временные пары и замены, проверяет запрет операций без входа, права каждого аккаунта, защиту от подмены площадки, журнал и выход. Временные пары/замены удаляются; записи аудита сохраняются.

## Выкладка на Vercel / production

В репозитории **нет production-секретов**. Приложение использует `DATABASE_URL`; `POSTGRES_URL` и `PRISMA_DATABASE_URL` кодом не читаются. Не заменяйте рабочие значения автоматически из-за пометки «Needs Attention».

1. Найдите существующий проект Vercel, связанный с `holfizz/tkiuk`, и подтвердите его production-домен. Локальная авторизация CLI проверяется через `vercel whoami`.
2. Сохраните отдельный backup БД и проверьте восстановление. Миграция `20261001000000_accounts_audit` только добавляет таблицы пользователей/сессий/аудита и nullable-поле площадки замен; расписание не удаляет. Миграция `20261001010000_week_override` добавляет явный флаг ручной настройки недели и индекс замен; существующие автоматически обновлявшиеся настройки не считаются ручной датой отсчёта.
3. Примените проверенную миграцию `prisma migrate deploy` с production-секретом в отдельном окружении, затем создайте три production-аккаунта с собственными паролями. Для аккаунтов production предусмотрен явный режим `npm run accounts:setup -- --production --apply` с отдельно переданным `DATABASE_URL` Prisma Postgres (SSL обязателен). Он создаёт недостающие аккаунты одной транзакцией, сохраняет существующие пароли и отказывается менять аккаунты с несовпадающими правами. Production-пароли сохраняются в `.local/production-accounts-<timestamp>.json` с правами `0600`.
4. Разверните новую сборку и проверьте вход/права. Загружайте новые расписания через защищённую админку для 2 площадки после резервного копирования.
5. Проверьте пятницу 9ПО-22к, обе площадки, замены и журнал действий. Для rollback приложения новые таблицы и поля можно оставить; старое расписание восстанавливается из backup или снимка `before` в журнале импорта.

Резервная копия production: `.local/backups/production-before-changes-2026-10-01.dump` (исключена из Git/Docker). Восстановление проверено в отдельной локальной БД `tkuik_restore_verify`: после обеих миграций сохранены все 2030 записей расписания с совпадающей контрольной суммой; все 34 замены определены как `SECONDARY`.

1 октября 2026 года по отдельному запросу пользователя в production применены обе новые миграции и созданы `dispatcher1`, `dispatcher2`, `admin` с независимыми паролями (по запросу пользователя сокращены до 12 символов; прежние пароли и сессии аннулированы). Свежая резервная копия перед этим: `.local/backups/production-before-accounts-20261001T133915Z.dump`. Все 2030 записей расписания остались неизменными (контрольная сумма совпала); 34 существующие замены получили площадку `SECONDARY`. Вход, серверные сессии, выход и запрет изменения чужой площадки проверены новой production-сборкой, подключённой к этой БД. Новые Excel-расписания в production пока не импортированы.

В Vercel найдены проекты `aitu` (`prj_zsFO0VuBAUQlOCZZrwRD2FkL0Sj5`) и `tkiuk` (`prj_zFnukp5c7ls9LMxZDYCOqvjw08O4`) команды `holfizzs-projects`. Просмотр их развёртываний возвращает 403 с требованием повторной авторизации для этой команды; CLI также не авторизован. Новая авторизация и название АИТУ подготовлены в коде, но ещё не опубликованы. Чтобы новые аккаунты заработали на опубликованном сайте, нужна повторная авторизация Vercel, проверка рабочего проекта и выкладка.
